# Phase 9: Code Review Report

**Reviewed:** 2026-05-27
**Depth:** standard
**Files Reviewed:** 19
**Status:** issues_found

## Summary

Phase 9 adds per-person performance scorecards, a leaderboard with configurable sort, configurable SLA/alert thresholds stored in `tenant_settings`, and alert badges on the Overview command center. The architecture is sound — queries are parameterized, money math stays in Postgres, currency grouping is enforced, and auth guards are consistently applied. However, four blockers were found: a wrong sort metric used for the `sla_breach` leaderboard (sorts by turnaround instead of breach rate — rendering that leaderboard mode incorrect), an incomplete IDOR guard on the OE scorecard that verifies user existence globally but not tenant membership for new engineers, a `?limit=` URL parameter that is generated by the "Load more" link but never read by the page (dead feature that silently shows the same 50 rows), and an `auditSlaHours=null` path in the SLA breach SQL that causes Postgres to treat the comparison as `EXTRACT(...) > NULL` — returning zero breach rate for every auditor when no threshold is provided instead of `null`.

## Critical Issues

### CR-01: `getAuditorSortFn` `sla_breach` branch sorts by `avgDecisionLatencyHours`, not by SLA breach rate

**File:** `src/actions/analytics.ts:1273-1279`

**Issue:** The `sla_breach` case in `getAuditorSortFn` reads `a.avgDecisionLatencyHours` / `b.avgDecisionLatencyHours` — the raw turnaround hours — and ranks highest first (DESC). The leaderboard UI labels this column "SLA Breach Rate" but actually ranks by raw turnaround hours descending — giving a meaningfully wrong ordering that a user would rely on to assign work.

### CR-03: `auditSlaHours = null` makes SLA breach rate SQL return 0 instead of `null`

**File:** `src/actions/analytics.ts:829-841`

**Issue:** When `options?.auditSlaHours` is not provided, `auditSlaHours` is set to `null` (line 829). This value is then interpolated into the Postgres query as a bound parameter `${auditSlaHours}` in the FILTER clause:

```sql
WHERE s.decided_at IS NOT NULL
  AND (EXTRACT(EPOCH FROM ...) / 3600.0) > ${auditSlaHours}  -- ${null}
```

In SQL, any comparison with `NULL` is `UNKNOWN`, which evaluates as false in a FILTER. So `COUNT(*) FILTER (WHERE ... > NULL)` returns `0`, and the breach rate becomes `0.0 / NULLIF(decided_count, 0)` = `0.0`, not `null`. The caller on line 869 correctly checks `options?.auditSlaHours != null` before setting `slaBreachRateDecided`, so the JS result is `null` as intended — but the DB query still runs with a wasteful `> NULL` comparison, and the behavior is fragile: any future caller that doesn't replicate that JS-level guard will silently report 0% breach rate for everyone.

```typescript
// FIX: skip the SLA breach computation entirely when auditSlaHours is null,
// by building a conditional sql fragment:
const slaBreachFragment = options?.auditSlaHours != null
  ? sql`
      COUNT(*) FILTER (
        WHERE s.decided_at IS NOT NULL
          AND (EXTRACT(EPOCH FROM (s.decided_at - s.submitted_at)) / 3600.0) > ${options.auditSlaHours}
      )::float
        / NULLIF(COUNT(*) FILTER (WHERE s.decided_at IS NOT NULL), 0)
    `
  : sql`NULL`;

// Then use ${slaBreachFragment} AS sla_breach_rate in the SELECT.
```

## Warnings

### WR-01: `getPortfolioKPIs` — `approvals_in_range` / `rejections_in_range` filter syntax is non-standard and fragile

**File:** `src/actions/analytics.ts:342-344`

**Issue:** The date condition is appended directly inside the FILTER clause of COUNT:

```sql
COUNT(*) FILTER (WHERE s.status = 'approved' ${dateCondition})   AS approvals_in_range
```

When `dateCondition` is non-empty it becomes `WHERE s.status = 'approved' AND s.submitted_at >= ... AND s.submitted_at < ...`. This works today but the Drizzle `sql.join` documentation notes that appending raw fragments inside `FILTER (WHERE ...)` is an unsupported pattern — it relies on Drizzle treating the raw `sql` interpolation as plain string concatenation rather than a subexpression. If the driver changes how it serialises inline fragments this silently breaks. The canonical approach is a CASE expression or a separate filtered sub-select.

**Fix:** Use a standard CASE inside COUNT or move to two CTEs:

```sql
COUNT(CASE WHEN s.status = 'approved'
           AND (${from} IS NULL OR s.submitted_at >= ${from})
           AND (${to}   IS NULL OR s.submitted_at < ${to})
      THEN 1 END) AS approvals_in_range
```

### WR-02: `ThresholdSettingsForm` — `Number(e.target.value)` converts empty string to `0`, bypassing `min=1` guards

**File:** `src/components/admin/ThresholdSettingsForm.tsx:118, 146, 172`

**Issue:** All three input `onChange` handlers call `Number(e.target.value)`. When the user clears an input, `e.target.value` is `""` and `Number("")` is `0`. The state is set to `0` immediately. On the next render the controlled input shows `0` (not empty). When the form is submitted, `auditSlaHours = 0` passes the JS check `Number.isInteger(0)` (true) but fails `auditSlaHours < 1` — so the error message is shown correctly. However, between clearing the field and submitting, the server action's Zod schema (`z.number().int().min(1).max(720)`) would also reject it if the client validation were bypassed, so there is no data-loss risk. The user experience is bad: clearing the field immediately snaps to `0` rather than allowing the user to type a new value.

**Fix:** Use `parseInt` / `parseFloat` and keep `NaN` as a controlled sentinel, or use an uncontrolled input with ref and parse only on submit.

### WR-03: `getPersonMetrics` auditor Query 3 includes pending submissions in `decisions_count`

**File:** `src/actions/analytics.ts:830-847`

**Issue:** Query 3 (auditor metrics) has:

```sql
COUNT(*) AS decisions_count
FROM submissions s
WHERE s.decided_by = ${personId}
  AND s.tenant_id  = ${tenantId}
  AND s.status IN ('approved', 'rejected')
```

The `decisions_count` alias is fine — but the AVG latency FILTER applies `WHERE s.decided_at IS NOT NULL`, while `COUNT(*)` at the top does not filter `decided_at IS NOT NULL`. A submission with `status = 'approved'` but `decided_at = NULL` (which should not exist given the audit flow, but the schema allows it — `decided_at` is nullable) would be counted in `decisions_count` but not in the AVG denominator, producing a misleading denominator for the SLA breach rate calculation on line 841. The denominator uses `NULLIF(COUNT(*) FILTER (WHERE s.decided_at IS NOT NULL), 0)` — not `decisions_count` — so the breach rate itself is consistent, but `metrics.decisionsCount` displayed in the UI would be inflated by any such orphan rows.

**Fix:** Add `AND s.decided_at IS NOT NULL` to the outer WHERE, or change the top-level `COUNT(*)` to `COUNT(*) FILTER (WHERE s.decided_at IS NOT NULL)`.

**File:** `src/app/dashboard/(admin)/people/page.tsx:283-300`
