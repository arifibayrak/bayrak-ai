<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → Server Actions | All mutations cross here; every action must require an authenticated office session |
| pending_people → people promotion | Office-controlled gate; only an authenticated office user may promote a pending person to active access |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Elevation of Privilege | unauthenticated Server Action calls | mitigate | Every action begins with `const session = await auth(); if (!session) throw new Error('Unauthorized')`; unit-tested via mocked null session |
| T-05-02 | Tampering | CSRF on Server Actions | accept | Next.js App Router Server Actions include built-in Origin-header CSRF protection (RESEARCH Security Domain) — accepted as framework-provided |
| T-05-03 | Information Disclosure | cross-tenant data exposure (D-09 hedge) | mitigate | All reads/writes scope tenant_id via getDefaultTenantId(); no query returns rows outside the seed tenant |
| T-05-04 | Tampering | partial promotion (orphaned person without assignment) | mitigate | approvePending wraps people-insert + assignment-insert + pending-delete in a DB transaction so a failure rolls all back |
| T-05-05 | Spoofing | manual add with arbitrary telegram id | mitigate | telegramUserId validated as positive integer; people.telegram_user_id is UNIQUE (no impersonation by duplicate id); office-only action |
</threat_model>
