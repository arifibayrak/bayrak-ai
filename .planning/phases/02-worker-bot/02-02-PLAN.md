<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Telegram callback_data → keyboard builders | callback_data strings produced here are later parsed and MUST be re-validated against the DB by handlers (Plan 04/05) — builders only emit IDs, they do not authorize |
| Telegram file API → Vercel Blob | the bot fetches an attacker-influenced file_path from Telegram and streams it to Blob |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04 | Tampering | crafted callback_data selecting an unassigned project/BOQ item | mitigate | Keyboard builders only emit `select:<id>` for items the worker was shown; the handler in Plan 05 re-validates the parsed ID against the worker's assignments/project boqItems before acting (RESEARCH Security Domain V4) — builders carry no trust |
| T-02-05 | Information disclosure | bot token leakage in photo URL construction | mitigate | TELEGRAM_BOT_TOKEN used only server-side to build the Telegram file URL; never stored in conversation_state, never returned to the client, never logged (RESEARCH anti-patterns) |
| T-02-06 | Denial of service / SSRF | oversized or malicious file from Telegram file URL | accept | The fetched URL is constructed only from Telegram's own `getFile` response (api.telegram.org host, fixed by the bot token) — not from arbitrary user input, so SSRF surface is bounded to Telegram's CDN. Single-photo upload fits the 55s/512MB function budget (vercel.json). File-size cap is a Phase 3+ hardening note. |
| T-02-SC | Tampering | npm installs | accept | No installs — @vercel/blob, grammy already installed and audited in Phase 1 |
</threat_model>
